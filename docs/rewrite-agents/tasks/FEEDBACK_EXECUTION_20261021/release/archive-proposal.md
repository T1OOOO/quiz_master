# Предложение архивации неиспользуемых Language Learner release trees

**Статус: пользователь явно одобрил 9 сборок21октября2026. Выполнение начато.** Проверенные результаты и фактические удаления будут зафиксированы отдельными квитанциями; этот исторический план сам по себе их не подтверждает.

## Что проверено

Свежий read-only снимок `2026-10-21` показал `/dev/vda2` (`ext4`) с
`8,531,845,120` свободными байтами из `102,417,174,528` (8.33%).
`/opt/ll/releases` находится на этом же filesystem. Поэтому создавать архив в
`/opt`, `/tmp` или рядом с исходным деревом нельзя: это временно требует ещё
один полный архив, не высвобождает места до удаления и не имеет доказанного
запаса.

Проверка `/proc` (cwd, cmdline и fd), Docker mounts и Kubernetes hostPath не
нашла ссылок на предложенные release paths на момент снимка. Node exporter
имеет read-only наблюдение `/`; это не является разрешением на удаление и не
заменяет проверку перед операцией. Сканирование повторяется непосредственно
перед каждым удалением.

Явно сохраняются `/opt/ll/assets`, Quiz Master, K3s/PVC, pgBackRest и три
свежих atlas-reader paths, перечисленные в companion JSON. Они не попадают ни
в архив, ни в `rm`.

## Точный первый пакет

В [archive-proposal.json](archive-proposal.json) перечислены девять абсолютных
paths. Их суммарный unique allocated размер — **9,555,880,176 bytes**;
скан по `(device,inode)` не обнаружил hardlink duplicates. Суммарный logical
размер — `9,134,946,750` bytes. Удаление *после подтверждённого off-host
архива* прогнозирует `18,087,725,296` свободных bytes (17.66%), то есть само
по себе не достигает release guard 20%; не следует выдавать его за достаточное
решение ёмкости.

Первый пакет намеренно не включает свежий
`atlas-reader-backend-20261021-0OPKKBZe`, хотя на момент снимка у него нет
process/mount reference. Это консервативное сохранение текущей LL работы.

## Условие для места архива

Нужен указанный пользователем off-host destination либо отдельный filesystem,
не `/dev/vda2`: например, проверенное удалённое хранилище. До старта он должен
иметь не менее **18,269,893,500 bytes** свободно: один uncompressed archive и
независимое распакованное дерево для проверки. Эта величина не предполагает
сжатие. На текущем сервере такого transient space нет.

## Выполняемая только после разрешения процедура

Для каждого path, по одному за раз:

1. Повторить `df`, `findmnt`, `/proc` cwd/cmdline/fd scan, Docker mount scan и
   Kubernetes hostPath scan. Остановиться при любой новой ссылке, mount,
   symlink, другой filesystem или изменившемся `(device,inode)` inventory.
2. Записать source manifest: relative path, mode, uid/gid, size, mtime,
   SHA-256 каждого regular file и aggregate SHA-256 manifest. Ещё раз вычислить
   `st_blocks*512`, unique allocation по `(st_dev,st_ino)` и file count.
3. Потоково записать non-compressed archive на off-host destination с
   `tar --numeric-owner --acls --xattrs --one-file-system`; локальный сервер не
   получает archive file. Записать SHA-256 archive и manifest рядом с ним.
4. Извлечь archive в отдельный verification directory **на destination**, не
   поверх source. Сверить там полный manifest, file count, modes/ownership,
   paths и SHA-256. Проверить `tar -tf` и отсутствие absolute/`..` members.
5. Сохранить receipt с source aggregate hash, archive hash, verification hash,
   destination URI, inventory и датой. Только после независимой проверки этого
   receipt разрешён один `rm -rf --one-file-system -- <literal-path>`.
6. До и после `rm` повторить active-reference scan; снять `df -B1 /` и
   подтвердить освобождённые allocated bytes. При несовпадении прекратить
   оставшиеся paths; archive остаётся rollback copy.

После Phase A нужна новая capacity inventory. Для дополнительной фазы требуются
новый exact candidate list и fresh inode-deduplicated allocation: существующий
снимок не доказывает, что другие UI/content releases всё ещё не нужны.

## Требуемое решение пользователя

Предлагаемое постоянное место архива: `E:/Backups/quiz-master/server-20261021/` вне репозитория и временной `.run`. Оно ещё не создавалось. Получено прямое разрешение: «Да, архивируй девять старых сборок, проверь архивы и удали распакованные копии. Затем выкладывай исправления на сервер и продолжай оставшиеся фидбеки».

Проверка файловой системы Windows не должна выдавать сохранение Unix-владельцев, ACL и xattrs за факт. Будущий исполнитель обязан отдельно доказать сохранность этих метаданных в архиве и возможность восстановления; если это не подтверждено, удаления не выполнять. После архива нужна новая инвентаризация с исключением пересекающихся кешей и фактическая проверка порога20%, а не сложение верхних оценок.

Уточнение процедуры проверки: на рабочей машине нет Linux-дистрибутива WSL, а свободной памяти сервера недостаточно для полного3,3ГБ дерева. Все записи каждого исходного TAR восстанавливаются в отдельные ограниченные Linux-деревья порциями32МБ/256записей с полной сверкой содержимого и Unix-метаданных; каждая исходная запись должна участвовать ровно один раз. Архив остаётся вне сервера. Код verifier прошёл независимый ACCEPT ac586e18, реальный небольшой fixture проверил наносекундное время, права, владельцев, xattr и симлинк. До удаления каждого оригинала нужны полная фактическая квитанция восстановления, отдельный независимый обзор этих доказательств и свежие проверки оригинала/использования.
