# LOTR package API pin split advisory

Read-only review of `docs/rewrite-agents/tasks/LOTR_PACKAGE_20261014/worker/prepare_lotr_package.py`, the actual ScreenSong52 package scripts under `.run/screen_song_package_20261014/package-v1/quiz-2026.10.14-screen-song-6866608/`, and the named metadata checkpoint. No scripts were run and no runtime/release work was performed.

## Pin split

Keep the baseline API pin `26e1657fd6259bdbbef9178cbe9343b775406d91c56cb9661d302ad530ab6f01` for verifying the immutable ScreenSong52 archive. In `prepare_lotr_package.py`, this is currently conflated in `API_SHA256` (line 24), the five-field baseline tuple in `load_release_pins` (lines 169–174), `verify_baseline_stage` (lines 597–608), `patch_cutover_text`'s required baseline guard (lines 663–680), and target `inject_version`/preparation receipt fields (lines 722–739 and 884). Split it into clearly named baseline and target pins.

The target is the ELF SHA-256 `f4d69555623aab2b8e1468fccb65256abefc9823d65214799b7e1475d4d9c850` (22,988,817 bytes), from `docs/rewrite-agents/tasks/LOTR_RUNTIME_METADATA_20261014/actual-linux-api-build.json`; the ELF itself is `.run/lotr_runtime_metadata_20261014/api-linux-amd64`. That receipt says exit 0, GOOS=linux, GOARCH=amd64, CGO_ENABLED=0, and API code checkpoint `9d842dfd641a2f288aef5f539c88d701b2d6c86c`; its own artifact hash is the pin. Add a separate target API artifact receipt pin and verify the receipt schema/exit/ELF/hash/code checkpoint, plus hash the artifact itself before copying it. Keep the ScreenSong52 archive/image/nginx/PVC pins and all source/Flutter receipt validation intact. Do not reinterpret `api_sha256` as both the archived baseline binary and new target binary.

There is a concrete missing step: `main()` extracts the immutable baseline, then copies target inputs and Web output, but never copies/replaces `stage/api` (`prepare_lotr_package.py` lines 828–840). Add one bounded copy of the verified target ELF to `stage/api` after `verify_baseline_stage` has authenticated the baseline and before checksums/archive creation. `verify_baseline_stage` must continue expecting the old API hash. The target metadata (`web/version.json`) and package-preparation receipt should report the new target API hash, while `baseline_input` continues to report the old baseline identity.

## Cutover and real runtime gate

The copied baseline `.run/.../cutover.sh` authenticates the current installed Helm image at line 12, then checks the release API at line 15 and the built image's `/app/api` at line 50 against the old `26e...` hash. The first guard is intentionally the currently deployed baseline; preserve it. Change the staged-release and candidate-image API checks (lines 15 and 50) to the new target hash, while keeping the baseline check in the Python archive verifier separate. The helper currently replaces the prior cutover image guard with `BASELINE_IMAGE` (helper lines 663–675), which correctly means “expected live image”; keep that meaning. Likewise, `patch_values_text` starts the generated values file on the baseline image, and the cutover script later changes the release values to the locally built candidate digest (baseline script lines 47–70); preserve that prepare-only digest flow. Keep `quiz_mode=prepare`, the PVC UID, nginx, archive checksum, `helm lint/template`, dry-run, and no-apply/early-exit guards.

The current `rehearse.py` starts `root/'api'` directly on a copied SQLite DB (lines 4–7, 23–34), then checks `/v1/catalog` and adjusts each live DTO's source URI and revision to canonical values before equality (lines 54–66). That is useful migration rehearsal but cannot establish the requested unmodified candidate-image contract. The cutover currently only checks candidate image file hashes and `nginx -t` (cutover lines 47–52); it does not run the candidate image's `/app/api` against the copied DB and assert raw, unmodified `/v1/catalog` output.

Add a distinct prepare-only gate that starts the built candidate image/container with only the copied rehearsal DB and expected content mount, calls the real HTTP API, and checks the returned DTOs before any normalization: all 100 LOTR questions, q93/q95 revision number 2 and reviewed SHA values, q93 opt-6 and q95 retained opt-5/key opt-2, all other 98 public projections byte/semantic-equal to the pinned public baseline, and all 145 playable Reader refs resolving to exact returned revision hashes. Preserve the current Reader snapshot/145-reference accounting and verify baseline receipts unchanged. A successful host-process rehearsal or image file SHA alone does not satisfy this gate. Container/db/process cleanup and non-published prepare-only behavior remain mandatory.

## Source and Flutter receipts

Do not loosen the existing `source_assets` exact-path/hash binding or the frozen `TARGET_SOURCE` check in `frozen_source_bytes` (`prepare_lotr_package.py` lines 156–233). Keep the new source review/export receipts required and cross-provider accepted; keep `verify_build_evidence` requiring separate production/QA builds, source-bound build ID, frozen embedded catalog/Reader assets, distinct output JS hashes, and browser receipt (lines 468–504). These receipts validate the frozen Flutter/client package, not the API ELF, so the API build receipt must be an additional proof input, not a replacement for them. Refresh controller source hashes/review only after implementing this bounded split; do not silently change historical source review hashes.

Recommended smallest implementation scope: constants + one target API proof field/validator + a verified target API copy step + distinct baseline-versus-target hashes in the generated metadata/receipt + target hash checks in the staged release/image while retaining the live baseline guard + a new unmodified candidate-image/Reader gate. No change is needed to historical archive identity, source review evidence, Flutter builds, or rollback model. Current `NEXT_STAGES_EN.md` accurately says this package is held, the previous API is not deployable approval, and DTO normalization is not runtime proof (lines 7–14); this advisory is not a release acceptance.
